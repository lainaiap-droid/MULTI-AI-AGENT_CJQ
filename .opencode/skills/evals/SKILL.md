# Evals

## Purpose

Skill запускает слой оценки качества артефактов и объясняет результат: какие проверки пройдены, какие провалены и к какому этапу вернуть исправление.

Evals — измерительный инструмент. Он не проектирует артефакты, не исправляет их и не принимает решение о переходе между этапами. Решение о Gate остаётся за `qa-lead`.

## Inputs

### Обязательные входные данные

- каталог кейса с `case.json`;
- артефакты кейса в `artifacts/` (requirement-review, jira-tasks, test-model, coverage-map);
- CLI `.opencode/evals/run-evals.mjs`.

### Опциональные входные данные

- фильтр по этапу (`--stage`);
- рубрика LLM-judge из `case.json`;
- внешняя команда оценки в `EVAL_JUDGE_CMD`;
- baseline предыдущего прогона;
- приватный кейс в `.opencode/evals/cases/private/`.

## Entry Criteria

Перед запуском проверь:

- кейс существует и содержит `case.json` с полями `id`, `title`, `judge.rubric`;
- артефакты лежат в `artifacts/` и названы `requirement-review*.md`, `jira-tasks*.md`, `test-model*.md`, `coverage-map*.md`;
- для запуска на реальных данных кейс находится в `cases/private/`, а не в публичном наборе;
- в артефактах и `source.md` нет секретов, PII и адресов пространства заказчика.

Если обязательных артефактов нет, запуск не имитируется: зафиксируй отсутствие и верни `BLOCKED`.

## Non-Goals

Skill не выполняет следующее:

- не изменяет и не переписывает артефакты;
- не создаёт, не изменяет и не удаляет сущности Jira и Qase;
- не запускает Test Runs;
- не принимает бизнес-решений и не отвечает на Open Questions;
- не заменяет Quality Gate и не отменяет его результат;
- не вызывает модель сам: judge получает промпт и возвращает JSON;
- не ослабляет проверки, чтобы кейс стал зелёным;
- не публикует приватные кейсы и результаты judge.

## Procedure

1. Проверь окружение: `node --version` не ниже 20.
2. Прогони самопроверку инструмента: `node .opencode/evals/run-evals.mjs --selftest`.
   Selftest обязан быть `PASS`, иначе результатам evals доверять нельзя.
3. Посмотри доступные кейсы: `node .opencode/evals/run-evals.mjs --list`.
4. Запусти нужный кейс:
   `node .opencode/evals/run-evals.mjs --case <CASE-ID> --verbose`.
5. Разбери провалы: для каждой проверки прочитай `id`, этап и `details`.
6. Если нужна семантическая оценка, подготовь промпты:
   `node .opencode/evals/run-evals.mjs --case <CASE-ID> --judge`.
7. Передай промпты из `<case>/_judge/<stage>.prompt.md` оценщику и положи ответы в `<case>/_judge/<stage>.scores.json`.
8. Повтори прогон с учётом оценок: `node .opencode/evals/run-evals.mjs --case <CASE-ID> --judge-ingest`.
9. Сформируй отчёт: `--md` и `--json` в каталог, который явно указал пользователь.
10. Верни короткий итог с вердиктом и адресными действиями по каждому провалу.

## Commands

| Команда | Назначение |
|---|---|
| `node .opencode/evals/run-evals.mjs` | все доступные кейсы |
| `--list` | перечень кейсов |
| `--case <ID>` | один кейс |
| `--stage <stage>` | только проверки этапа и общие |
| `--verbose` | детали провалов и предупреждений |
| `--judge` | подготовить промпты judge и выполнить `EVAL_JUDGE_CMD`, если задан |
| `--judge-ingest` | учесть готовые `_judge/*.scores.json` |
| `--md <path>` / `--json <path>` | отчёт в файл |
| `--baseline <path>` / `--update-baseline` | сравнение с предыдущим прогоном |
| `--selftest` | мутационная самопроверка инструмента |

Коды выхода: `0` — все кейсы PASS, `1` — есть ошибки, `2` — кейсы или оценки judge не найдены.

## Check Families

| Семейство | Что проверяет |
|---|---|
| `FM-*` | frontmatter: обязательные поля, статус, версия, формат `run_id` |
| `ST-*` | обязательные секции, Gate Self-Check, отсутствие шаблонных заглушек |
| `ID-*` | формат и уникальность идентификаторов, непрерывность нумерации |
| `TR-RR-*` | трассировка требований, ссылки на BR/AC и источник |
| `TR-JIRA-*` | поля задач, допустимые Issue Type и приоритеты, согласованность Coverage |
| `TR-TEST-*` | поля сценариев, типы, приоритеты, ожидаемые результаты, согласованность Coverage |
| `CV-*` | статусы Coverage Map, арифметика сводки, перечень GAP |
| `HY-*` | секреты, PII, абсолютные пути, адреса пространства, маркеры запуска |
| `X-*` | согласованность бандла: общий `run_id`, корректные версии |
| `EV-*` | минимальный ожидаемый объём артефактов из `case.json` |

`severity=error` влияет на вердикт, `severity=warn` — только сигнал.

## LLM-Judge

Judge не вызывается из CLI напрямую. Возможны два пути:

1. `EVAL_JUDGE_CMD` — внешняя команда получает промпт в stdin и возвращает JSON с оценками.
2. Агент или человек читает `<stage>.prompt.md`, оценивает по рубрике и сохраняет `<stage>.scores.json`.

Формат оценок:

```json
{
  "case": "<CASE-ID>",
  "stage": "<stage>",
  "judge": "<модель или human>",
  "scores": [
    { "id": "J-FAITHFUL", "score": 3, "max": 3, "comment": "<обоснование>" }
  ],
  "verdict": "PASS"
}
```

Правила приёма оценок:

- каждый критерий рубрики присутствует ровно один раз;
- балл — число в диапазоне `0..weight`;
- у каждой оценки есть непустое обоснование;
- порог PASS — не менее 75% взвешенной суммы;
- при некорректных оценках вердикт `FAIL`, причина указывается в отчёте.

## Dataset

- `cases/public/<CASE-ID>/` — синтетические обезличенные кейсы, коммитятся.
- `cases/private/<CASE-ID>/` — реальные страницы Confluence, не коммитятся.
- `case.json` задаёт `id`, `title`, `source_file`, `expect` и рубрику judge.
- `source.md` — входные требования кейса.
- `artifacts/` — эталонные артефакты, по которым считается качество.
- `_judge/` — промпты и оценки, не коммитятся.

Новый публичный кейс допустим только с синтетическими данными. Реальные требования, токены, email, accountId и адреса пространства в публичный набор не попадают.

## Rules

- не изменяй артефакты и `case.json` ради зелёного результата;
- не отключай проверку и не повышай порог judge без явного решения пользователя;
- не считай eval-вердикт заменой Quality Gate;
- не публикуй содержимое `cases/private/` и `_judge/`;
- не запускай evals на данных, содержащих секреты;
- если проверка ошибочно срабатывает на корректном артефакте, сначала проверь артефакт, затем правило; исправление правила требует отдельного согласования;
- при расхождении результата selftest и кейса доверяй selftest и разбирайся в причине.

## Output

Верни краткий отчёт:

```yaml
status: PASS | FAIL | BLOCKED
cases:
  - id: <CASE-ID>
    verdict: PASS | FAIL
    score: <0-100>
    failed_checks: [<ID>, ...]
judge:
  verdict: PASS | FAIL | NOT_RUN
  earned: <n>
  total: <n>
artifacts:
  - <path к md/json отчёту, если запрошен>
next_actions:
  - <к какому этапу и что вернуть>
```

## Completion Criteria

- selftest выполнен и пройден;
- для запрошенного кейса получен детерминированный вердикт;
- каждый провал назван по `id` проверки и этапу;
- оценки judge, если использовались, прошли валидацию;
- приватные данные не опубликованы;
- итог содержит адресное следующее действие, а не общую рекомендацию.

## Handoff

`qa-lead` получает только короткий header выше. Полный отчёт остаётся в файле, который указал пользователь. Skill не задаёт вопросы пользователю напрямую.
