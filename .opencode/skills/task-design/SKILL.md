# Task Design

## Purpose

Skill преобразует проверенный Requirement Review в структурированный Jira Tasks Artifact, пригодный для последующего создания задач через Jira Tool.

Skill проектирует содержание задач. Он не выполняет запись в Jira и не управляет Jira Tool напрямую.

## Inputs

### Обязательные входные данные

- валидный Requirement Review Artifact
- Scope текущей задачи агента

### Опциональные входные данные

- проектные правила декомпозиции задач
- допустимые типы задач и правила их выбора, если они заданы Context
- проектные правила оформления Acceptance Criteria
- приоритеты или ограничения, явно переданные агентом
- кандидаты в дубликаты из существующих Jira-задач, если агент уже получил их через Jira Tool

## Entry Criteria

Перед выполнением проверь:

- Requirement Review Artifact существует и доступен;
- `status` артефакта — `READY`, либо `PARTIAL` с явно принятыми ограничениями, которые не мешают декомпозиции;
- артефакт содержит Requirements, Business Rules, Acceptance Criteria и Source References;
- Scope текущей задачи определён;
- критические Ambiguities и Conflicts, влияющие на декомпозицию, либо разрешены, либо явно помечены.

Если Requirement Review имеет `status: BLOCKED` или критическая неоднозначность не позволяет надёжно сформировать задачу, верни `BLOCKED` с указанием зависимости. Не заполняй пробелы самостоятельно.

## Non-Goals

Skill не выполняет следующее:

- не создаёт задачи в Jira;
- не выбирает Jira Project, Assignee, Sprint, Fix Version, Story Points и другие проектные поля;
- не заполняет поле Priority в Jira;
- не ищет дубликаты в Jira самостоятельно;
- не придумывает Acceptance Criteria и бизнес-правила;
- не проектирует тестовую модель и тест-кейсы;
- не проектирует реализацию или архитектуру кода;
- не изменяет Requirement Review.

## Context Management

- используй Requirement Review как основной Source of Truth для проектирования задач
- не возвращайся к полной истории чата, если необходимая информация уже содержится в валидном Requirement Review
- не используй существующие Jira-задачи как замену исходным требованиям
- если агент передал данные о существующих задачах, используй их только для предотвращения дублирования и согласования декомпозиции
- не запрашивай Jira самостоятельно: Tool-вызовы выполняются агентом согласно Agent Instruction
- не используй проектные значения, которые не переданы Context

## Procedure

1. Определи, какие подтверждённые требования требуют отдельной работы команды разработки
2. Сгруппируй связанные требования в логически целостные задачи
3. Разделяй задачи, если они имеют разные цели, разные критерии приёмки, независимые риски или могут реализовываться отдельно
4. Не дроби работу на задачи без самостоятельной ценности или проверяемого результата
5. Для каждой задачи сформируй понятный Summary
6. Сформируй Description на основании Requirement Review
7. Определи Issue Type по правилам ниже
8. Добавь Acceptance Criteria только из подтверждённых требований или явно переданного проектного Context
9. Сохрани Traceability к исходным требованиям
10. Укажи зависимости между задачами, если они следуют из Requirement Review
11. Назначь `Priority (design)` только если она может быть обоснована риском, бизнес-критичностью или явным Context
12. Выяви потенциальные дубли относительно переданной информации о существующих Jira-задачах
13. Сформируй Jira Tasks Artifact

## Issue Type

Правила выбора:

- Если Context задаёт допустимые типы и правила выбора — следуй им.
- **Epic** — только если группа требований охватывает несколько независимо поставляемых задач и проект поддерживает эпики. Не создавай Epic для одной задачи.
- **Task** — независимо поставляемая и проверяемая единица работы. Это нейтральный вариант по умолчанию, если Context не задаёт другой контракт.
- **Sub-task** — только если в Artifact уже есть родительская задача и часть работы не имеет самостоятельной ценности.
- Если тип нельзя обосновать, укажи `NEEDS_PROJECT_CONTEXT` и вынеси вопрос в Open Questions.

Если выбран тип по умолчанию, явно отметь `Issue Type source: default`.

## Acceptance Criteria

- Используй только AC, которые есть в Requirement Review или явно переданы проектным Context.
- Форматирование в Given/When/Then или чек-лист допустимо, если не меняет смысл.
- Запрещено добавлять новые условия, пороги, исключения или ожидаемое поведение.
- Если для требования AC отсутствуют, укажи `AC: MISSING` и добавь Open Question.
- Не превращай риск или рекомендацию в Acceptance Criteria.

## Priority

- `Priority (design)` — атрибут проектирования задачи.
- Допустимые значения: `HIGH`, `MEDIUM`, `LOW`, `NEEDS_HUMAN_DECISION`.
- Основание: риск, бизнес-критичность или явный Context.
- Поле Priority в Jira не заполняется. Это делает только `qa-lead` и только при наличии отдельного разрешения.

## Boundary with Test Design

Task Design определяет, что нужно сделать команде разработки. Он не определяет, как это проверять.

- Acceptance Criteria описывают проверяемый результат задачи, а не тестовые сценарии.
- Шаги, тестовые данные и Test Model создаёт Skill `test-design`.
- Если Requirement Review не содержит достаточных данных для задачи, верни `BLOCKED` или Open Question, а не додумывай поведение.

## Rules

- не создавай задачу, если для неё нет основания в Requirement Review
- не добавляй Acceptance Criteria, которых нет в подтверждённых требованиях
- не разрешай бизнес-неоднозначности самостоятельно
- не смешивай в одной задаче независимые изменения без обоснованной причины
- не создавай несколько задач, описывающих одно и то же изменение
- не определяй Jira Project, Assignee, Sprint, Fix Version, Story Points или другие проектные поля самостоятельно, если они не переданы Context
- не заполняй Jira priority field
- не вызывай Jira Tool
- не изменяй существующие Jira-задачи
- не указывай Jira Issue Key как фактически созданный, пока агент не получит подтверждение от Jira Tool
- не создавай тест-кейсы и тестовую модель

## Reasoning Patterns

### Branching / Tree

Может применяться, если существуют несколько существенно разных вариантов декомпозиции требований. Сформируй не более трёх вариантов, сравни их по атомарности, трассируемости, зависимостям задач, риску дублирования и удобству реализации, затем выбери наиболее обоснованный.

### Self-Refine / Critic

После формирования Jira Tasks Artifact проверь его по Completion Criteria. Исправь дубли, чрезмерно крупные задачи, потерю требований или необоснованные Acceptance Criteria.

## Output

Создай Jira Tasks Artifact. Для каждой задачи укажи:

- Local ID или временный идентификатор
- Summary
- Issue Type и основание выбора
- Description
- Source Requirements
- Acceptance Criteria или `AC: MISSING`
- Dependencies, если применимо
- Priority (design) или `NEEDS_HUMAN_DECISION`
- Traceability `TASK → REQ/BR/AC`
- Open Questions или Blockers, если они влияют на создание задачи

Jira Issue Key не должен присутствовать как фактически созданный, пока агент не выполнит Jira Tool и не получит подтверждение.

## Artifact Contract

- **Producer:** Skill task-design.
- **Consumer:** Agent, этап создания задач через Jira Tool.
- **Artifact:** Jira Tasks.
- **Validation:** Completion Criteria этого Skill.
- **Error Handling:** если Requirement Review содержит критическую неоднозначность, не позволяющую надёжно сформировать конкретную задачу, пометь соответствующую часть как `BLOCKED` или `REQUIRES_HUMAN_DECISION` вместо самостоятельного выбора.

## Completion Criteria

- Entry Criteria выполнены
- каждая задача имеет основание в Requirement Review
- каждое значимое подтверждённое требование либо покрыто задачей, либо явно отмечено как не требующее отдельной задачи
- Summary и Description понятны без повторного чтения всей истории агента
- Issue Type определён и обоснован
- Acceptance Criteria не содержат придуманных бизнес-правил
- отсутствующие AC явно помечены
- `Priority (design)` отделён от поля Priority в Jira
- Traceability к требованиям сохранена
- необоснованные дубликаты отсутствуют
- критические Ambiguities и Conflicts не скрыты
- Artifact готов к передаче агенту для создания задач через Jira Tool

## Artifact Template

Шаблон: `templates/jira-tasks.md` относительно каталога skill.

Имя файла: `jira-tasks.v<n>.md` в каталоге запуска.

## Handoff

Верни `qa-lead` только короткий header:

```yaml
status: READY | PARTIAL | BLOCKED
artifact: <path>
summary: "<3–7 строк>"
key_findings: [...]
blockers: [...]
questions_for_human: [...]
```

Не возвращай полный текст артефакта и не задавай вопросы пользователю напрямую.
