# Requirement Review

## Purpose

Skill выполняет систематическое ревью требований и формирует проверенный Requirement Review Artifact, который используется следующими этапами Agent Workflow.

Skill отвечает только за анализ требований. Он не проектирует Jira-задачи, не создаёт тестовую модель и не выполняет действия во внешних системах.

## Inputs

### Обязательные входные данные

- актуальные требования текущей функциональности, полученные агентом из Confluence
- ссылка, идентификатор или иной reference на исходный источник требований
- определённый Scope анализируемой функциональности

### Опциональные входные данные

- критерии приёмки
- связанные бизнес-правила и ограничения
- релевантная связанная документация
- подтверждённые проектные соглашения
- дополнительный Context, явно предоставленный агентом

## Entry Criteria

Перед выполнением проверь:

- source artifact существует и доступен для чтения;
- source содержит `page_id`, `page_version`, `source_status`, `URL` и `retrieved_at`;
- `source_status` (Content status страницы) равен `Verified` или `approved` без учёта регистра, либо есть явное подтверждение от PO/BA;
- Scope функциональности определён;
- переданный Context относится к той же функциональности.

`source_status` берётся из Content status страницы (поле `contentStatus.name`), а не из lifecycle-статуса `status`. Lifecycle-статус `current` означает только «опубликована» и подтверждением не является.

Если `source_status` не входит в допустимый список (`Verified`, `approved`):

- не используй фрагмент как подтверждённое требование;
- пометь его `UNCONFIRMED`;
- зафиксируй `Missing Information` и `Open Questions`;
- верни `status: BLOCKED`, если без подтверждения нельзя надёжно выполнить ревью;
- верни `status: PARTIAL` с явным ограничением, если ревью возможно, но часть выводов зависит от неподтверждённых данных.

Если обязательный вход отсутствует, верни `BLOCKED` с описанием причины. Не заполняй пробелы предположениями.

## Non-Goals

Skill не выполняет следующее:

- не создаёт Jira-задачи;
- не проектирует тестовые сценарии, шаги, preconditions, тестовые данные и Expected Result конкретного теста;
- не строит Test Model;
- не принимает бизнес-решения;
- не изменяет исходные требования;
- не ищет данные в Jira, Qase или Confluence самостоятельно;
- не придумывает отсутствующие Acceptance Criteria.

## Context Management

- используй только данные, относящиеся к анализируемой функциональности
- не используй устаревшие версии требований, если доступна более актуальная версия
- не используй предыдущие выводы агента как Source of Truth, если их можно проверить по исходным требованиям
- при большом объёме документации анализируй только релевантные фрагменты, переданные агентом
- не загружай и не запрашивай самостоятельно данные из Jira или Qase: внешние Tools управляются Agent Instruction
- если входного Context недостаточно, явно зафиксируй Missing Information
- не переноси историю предыдущих сессий и кэш между сессиями

## Procedure

1. Определи Scope анализируемой функциональности
2. Выдели явно сформулированные функциональные требования
3. Выдели бизнес-правила и ограничения
4. Выдели Acceptance Criteria только там, где они явно определены
5. Определи зависимости между требованиями и связанными функциями
6. Найди неоднозначные формулировки, допускающие несколько интерпретаций
7. Найди внутренние противоречия между требованиями
8. Определи отсутствующую информацию, необходимую для однозначного понимания ожидаемого поведения
9. Выдели правила валидации и значимые граничные условия, если они следуют из требований
10. Определи основные Positive Flows и Negative Flows, которые прямо следуют из требований
11. Определи QA-риски, связанные с требованиями
12. Сформируй Open Questions для спорных и неполных требований
13. Сформируй структурированный Requirement Review Artifact

## Rules

- не придумывай отсутствующие требования, бизнес-правила, ограничения или Acceptance Criteria
- не выдавай предположение за подтверждённое требование
- не разрешай бизнес-неоднозначности самостоятельно
- если два авторитетных фрагмента противоречат друг другу, зафиксируй Conflict
- каждый существенный вывод должен иметь Source Reference; если источник недоступен, это должно быть явно указано как ограничение
- Acceptance Criteria можно нормализовать по формулировке, но нельзя добавлять новые условия, пороги или ожидаемое поведение
- если Acceptance Criteria отсутствуют, зафиксируй это в Missing Information или Open Questions и не создавай их самостоятельно
- не создавай Jira-задачи
- не создавай тест-кейсы и тестовую модель
- не изменяй исходные требования
- не назначай Priority: это не входит в scope ревью требований
- Risk или Recommendation не должны подменять исходное Requirement

## Boundary with Test Design

Requirement Review фиксирует:

- поведение и правила на уровне требований;
- Validation Rules и значимые Boundaries, если они следуют из требований;
- Positive Flows и Negative Flows на уровне описанного поведения;
- QA-риски и открытые вопросы.

Requirement Review не фиксирует:

- тестовые сценарии и их количество;
- шаги, preconditions и тестовые данные;
- Expected Result конкретного теста;
- приоритет тест-кейса.

Эти элементы создаёт Skill `test-design`. Если Requirement Review начинает описывать конкретные проверки, это нарушение границы.

## Reasoning Pattern

### Self-Refine / Critic

После формирования первого варианта Requirement Review проверь его по Completion Criteria. Если обнаружены исправимые недостатки, уточни Artifact и выполни повторную проверку.

Максимальное количество циклов исправления определяется Agent Instruction. Skill не должен инициировать бесконечное самоуточнение.

### Branching / Tree

Не применяется по умолчанию. Если требование допускает несколько существенно разных трактовок, Skill не выбирает одну ветвь, а фиксирует Ambiguity и варианты трактовки для эскалации.

## Output

Создай Requirement Review Artifact со следующей структурой:

- Scope
- Source References
- Requirements
- Business Rules
- Acceptance Criteria
- Validation Rules
- Dependencies
- Ambiguities
- Missing Information
- Conflicts
- Positive Flows
- Negative Flows
- Boundaries
- Risks
- Open Questions
- Traceability

Каждый артефакт содержит frontmatter со статусом `READY`, `PARTIAL` или `BLOCKED`.

## Artifact Contract

- **Producer:** Skill requirement-review.
- **Consumers:** Skill task-design и Skill test-design.
- **Artifact:** Requirement Review.
- **Validation:** Completion Criteria этого Skill.
- **Error Handling:** если обязательный вход отсутствует или критическая неоднозначность не позволяет сформировать надёжный Artifact, вернуть `BLOCKED` с описанием причины, а не заполнять пробелы предположениями.

## Completion Criteria

- Entry Criteria выполнены или явно зафиксированы ограничения
- все предоставленные релевантные требования проанализированы
- явные Requirements, Business Rules и Acceptance Criteria выделены
- Ambiguities и Conflicts либо зафиксированы, либо явно указано, что они не обнаружены
- Missing Information зафиксирована
- Validation Rules и значимые Boundaries отражены там, где они следуют из требований
- Positive и Negative Flows определены в пределах доступных требований
- QA Risks и Open Questions зафиксированы
- существенные выводы имеют Source References
- Acceptance Criteria не содержат добавленных условий
- Artifact не содержит придуманных требований
- Artifact не содержит тестовых сценариев, шагов и Expected Result

## Artifact Template

Шаблон: `templates/requirement-review.md` относительно каталога skill.

Имя файла: `requirement-review.v<n>.md` в каталоге запуска.

## Handoff

Верни `qa-lead` только короткий header:

```yaml
status: READY | PARTIAL | BLOCKED
artifact: <path>
summary: "<3–7 строк>"
key_findings: [...]
blockers: [...]
questions_for_human: [...]
```

Не возвращай полный текст артефакта и не задавай вопросы пользователю напрямую.
